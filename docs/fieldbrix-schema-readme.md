# Field Service Platform — Database Schema Reference

This document describes every table, column, type, constraint, and index in
`field_service_platform_schema.sql`, and explains *why* each piece exists.
It is meant as a companion reference for engineers building against or
reviewing this schema.

## 1. What this schema is for

The schema backs a **multi-tenant field service management platform**:
companies ("tenants") that dispatch field workers to customer sites to
perform inspections, maintenance, installs, or repairs, guided by
configurable digital checklists ("workflows"). Core capabilities modeled:

- **Multi-tenancy** with hard data isolation between companies.
- **Configurable workflows** — tenants build their own dynamic forms
  (sections, fields, conditional rules) without code changes, and version
  them safely.
- **Scheduling & recurrence** — one-off tasks and recurring maintenance
  plans (e.g. "service this AC unit every 90 days").
- **Offline-first mobile execution** — field workers fill out workflows on
  devices that may be offline; answers, photos, GPS, and signatures sync
  back with idempotent conflict handling.
- **Evidence & compliance** — photos, signatures, OTP customer
  confirmations, GPS breadcrumbs, and exceptions (safety stops, GPS
  mismatches, failed validations) are captured for audit and compliance.
- **Review workflow** — supervisors approve/reject submitted work.
- **Reporting & audit** — generated PDF/report artifacts and an
  append-only audit log for every mutation.

## 2. Global conventions

| Convention | Detail | Why |
|---|---|---|
| Primary keys | `uuid`, generated by the application (UUIDv7) | UUIDv7 is time-ordered, so it indexes/sorts almost as well as a sequence while still being safe to generate client-side (offline mobile clients can create IDs before they ever reach the server) and safe to expose externally. |
| Multi-tenant tables | Composite PK `(tenant_id, id)`, and every FK carries `tenant_id` alongside the referenced id | Guarantees a row can never be joined/referenced across tenant boundaries even if application code forgets a `WHERE tenant_id = ...` clause — the foreign key itself enforces same-tenant linkage. This is the single most important structural pattern in the schema. |
| Row-Level Security | `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY` + a `tenant_isolation` policy on every tenant-scoped table, keyed off `current_setting('app.tenant_id')` | Defense-in-depth: even if an application bug or a raw SQL console session omits a tenant filter, Postgres itself refuses to return or write rows outside the session's tenant context. `SET LOCAL app.tenant_id = '<uuid>'` must be run per transaction. |
| Timestamps | `timestamptz`, defaulting to `clock_timestamp()` | `timestamptz` stores absolute instants (safe across tenant timezones); `clock_timestamp()` (not `now()`) is used so defaults reflect actual wall-clock time even within long transactions, rather than transaction-start time. |
| `updated_at` maintenance | `set_updated_at()` trigger attached to mutable tables | Removes the risk of application code forgetting to bump `updated_at` on `UPDATE`; guarantees the column is trustworthy for sync/cache-invalidation logic. |
| Soft delete | `deleted_at timestamptz` on reference data (customers, sites, service_targets) | These entities are referenced by historical tasks/reports that must remain valid forever, so rows are archived, never hard-deleted. |
| Codes | `citext` for human-entered unique codes (slugs, employee codes, part codes, etc.) | Case-insensitive equality/uniqueness without forcing the application to normalize case before every lookup or insert. |
| JSONB "policy"/"settings" columns | e.g. `evidence_policy`, `validation`, `permission_overrides`, `feature_flags` | These represent tenant-configurable, schema-light rules (validation logic, feature toggles, per-field capture policy) that vary per workflow/field/tenant and would otherwise require constant DDL migrations. JSONB keeps configuration data-driven. |
| Extensions | `citext`, `pg_trgm`, `btree_gin` | `citext` for case-insensitive text; `pg_trgm` for fuzzy/fast `ILIKE`-style name search (customers, parts); `btree_gin` to allow composite GIN indexes mixing scalar and trigram columns. |

## 3. Enumerated types

Enums are used instead of free-text/lookup tables wherever the value set is
fixed by the *system* (not tenant-configurable) and small. This gets
constraint-level validation (invalid values are rejected at the database,
not just the application) and a compact on-disk representation.

| Enum | Values | Why it exists |
|---|---|---|
| `user_status` | active, disabled | Platform-level login gating, independent of any tenant membership. |
| `tenant_status` | trial, active, suspended, closed | Drives billing/access gating at the company level (e.g. suspended tenants can't log in, closed tenants are read-only). |
| `membership_role` | company_admin, supervisor, field_worker | The three-tier permission model: admins configure, supervisors assign/review, field workers execute. |
| `membership_status` | invited, active, disabled | Tracks the user-invitation lifecycle within a tenant separately from the platform-level `user_status`. |
| `workflow_status` | active, archived | Whether a workflow (the template family) can still be selected for new tasks. |
| `workflow_version_status` | draft, published, archived | Enforces the draft → published → archived lifecycle so in-progress edits never affect live tasks. |
| `field_type` | section, instruction, text, large_text, number, boolean, single_choice, multiple_choice, date, time, datetime, gps, image, file, scanner, lookup, signature, otp, repeatable_group, calculated | The full palette of input/display widgets the dynamic form builder supports, covering data capture, media evidence, structured references, and computed values. |
| `rule_conjunction` | and, or | Boolean joiner between condition groups in conditional-logic rules. |
| `rule_operator` | equals, not_equals, contains, ... (29 total) | Every comparison a conditional rule can perform against a field's answer — covering text, numeric ranges, selections, dates, GPS radius/accuracy, counts, and target-value matching. A large operator set is necessary because the workflow engine must express real inspection logic ("if reading is outside range", "if GPS accuracy too poor", "if selected count below N") without code. |
| `rule_action_type` | show, hide, require, ... (17 total) | What a rule can *do* once its conditions match: control field visibility/requiredness, force extra evidence, block submission, escalate for review, or flag an exception. This is the dynamic-forms engine's action vocabulary. |
| `recurrence_status` | draft, active, paused, ended | Lifecycle of a recurring maintenance schedule, independent from any single generated task. |
| `task_priority` | low, normal, high, urgent | Dispatch/triage ordering. |
| `task_status` | draft, assigned, accepted, in_progress, paused, submitted, rejected, completed, cancelled | The full task lifecycle state machine, including the review loop (`submitted` → `rejected` → back to work) and worker-side pause/resume. |
| `task_result` | passed, partial, failed, safety_stop, follow_up_required | Business outcome of the work performed, distinct from workflow `task_status` — lets reporting answer "was the equipment OK?" separately from "is the paperwork done?". |
| `task_link_type` | follow_up, rework, duplicate, related | Typed relationships between tasks (e.g. a failed inspection spawning a follow-up repair task), preserving service history lineage. |
| `task_run_state` | draft, submitted, rejected, approved | State of one *submission attempt* (see `task_runs`), separate from the parent task's overall status. |
| `answer_validation_status` | unvalidated, valid, warning, invalid | Result of running a field's `validation` rules against its captured answer, computed client- or server-side. |
| `section_result` | pass, warning, partial, fail, blocked, not_applicable | Aggregated pass/fail rollup per workflow section per run, used for report generation and dashboards. |
| `evidence_type` | image, file, signature | The kinds of binary evidence a task run can attach. |
| `capture_source` | camera, gallery, file_picker, generated | Provenance of evidence — distinguishes live-captured photos (higher trust, tamper-resistant for compliance) from gallery uploads or system-generated files (e.g. signature images, generated PDFs). |
| `upload_status` | pending, uploading, uploaded, failed | Tracks the async binary-upload pipeline separately from metadata row creation, which is essential for offline-first clients that write metadata before the file body finishes uploading. |
| `gps_event_type` | duty_start, duty_end, check_in, check_out, evidence_capture | The moments at which location is sampled, used to reconstruct a worker's day and to prove presence at a site. |
| `confirmation_method` | signature, otp, none | How customer sign-off on completed work is captured. |
| `confirmation_status` | confirmed, customer_unavailable, customer_refused, not_required | Outcome of the confirmation attempt, including the negative cases that must still be recorded for accountability. |
| `exception_type` | safety, gps, target_mismatch, validation, final_test, customer_confirmation, sync, other | Categorizes anomalies raised during a task so they can be routed/reported by kind (e.g. safety exceptions may page a supervisor immediately). |
| `exception_severity` | info, warning, critical | Triage priority for the exceptions queue. |
| `exception_status` | open, accepted, resolved, dismissed | Exception handling lifecycle — distinguishes "acknowledged as-is" from "actually fixed" from "false positive". |
| `review_decision` | approved, rejected, follow_up_required | Supervisor's verdict on a submitted task run. |
| `request_status` | pending, approved, rejected | Generic approval-queue status, reused for ad-hoc asset registration requests. |
| `device_status` | active, revoked | Lets a tenant admin kill a lost/stolen device's access (push token, sync) without touching the user account. |
| `sync_mutation_status` | received, applied, rejected, duplicate | Server-side outcome of an offline mutation replay, needed for the client to know what actually landed. |
| `import_type` | users, customers, sites, service_targets, parts, tasks | Which entity a bulk CSV/spreadsheet import job is loading. |
| `import_status` | uploaded, validating, ready, processing, completed, failed | Bulk-import pipeline stages, surfaced to the admin UI as progress. |
| `import_row_status` | valid, warning, rejected, created, updated | Per-row outcome within an import job, for the row-level error report. |
| `notification_status` | unread, read, dismissed | In-app notification inbox state. |

## 4. Shared trigger function

```sql
CREATE OR REPLACE FUNCTION set_updated_at() ...
```
Sets `NEW.updated_at := clock_timestamp()` on every `UPDATE`. Attached via a
`DO $$ ... $$` loop to: `users, tenants, tenant_settings, branches,
tenant_users, teams, customers, sites, service_targets, parts, workflows,
recurrence_plans, tasks, device_installations, task_answers`.
**Why:** centralizes "last modified" bookkeeping in one trigger function
instead of duplicating `updated_at = clock_timestamp()` in every UPDATE
statement across the application — and it can't be forgotten.

## 5. Tables

### 5.1 `users`
Platform-wide person record. One human can belong to multiple tenants via
`tenant_users`.

| Column | Type | Why |
|---|---|---|
| `id` | uuid PK | Stable platform-wide identity, independent of any tenant. |
| `auth_subject` | text, unique | The identifier from the external auth provider (e.g. IdP subject/sub claim) — decouples login identity from application data. |
| `email` | citext | Case-insensitive login/contact channel. Nullable because phone-only accounts are allowed. |
| `phone_e164` | text | SMS/OTP delivery and contact; E.164 format keeps it unambiguous internationally. |
| `display_name` | text | Human-readable name shown in UI. |
| `status` | user_status | Global kill switch (disable a compromised account across all tenants at once). |
| `last_login_at` | timestamptz | Security auditing / stale-account detection. |
| `created_at`, `updated_at` | timestamptz | Standard bookkeeping. |
| CHECK `users_contact_ck` | email IS NOT NULL OR phone_e164 IS NOT NULL | A user must be reachable by at least one channel (for OTP, notifications, password reset). |
| Unique indexes | `email` / `phone_e164` where not null | Case-insensitive dedupe on whichever channel is present, without rejecting rows that only have the other channel. |

### 5.2 `platform_admins`
| Column | Type | Why |
|---|---|---|
| `user_id` | PK, FK → users, `ON DELETE RESTRICT` | Marks a platform (not tenant) support/ops user. `RESTRICT` prevents deleting a user who still holds admin rights without explicitly demoting them first. |
| `role` | text | Free-text platform role (e.g. "support", "billing_ops") — internal team, doesn't need enum-level rigor. |
| `created_at` | timestamptz | Audit of when elevated access was granted. |

### 5.3 `tenants`
The company/customer of the platform itself.

| Column | Type | Why |
|---|---|---|
| `id` | uuid PK | Root of all tenant-scoped data — every other tenant table's FK chain terminates here. |
| `slug` | citext, unique | URL-safe/human identifier (subdomain, API path segment). |
| `legal_name`, `display_name` | text | Legal name for contracts/invoicing vs. the friendly name shown in-product. |
| `status` | tenant_status | Drives access gating (trial/suspended/closed). |
| `default_timezone` | text | Default for scheduling display when a branch/site doesn't specify its own. |
| `default_locale` | text | Default UI language. |
| `plan_code` | text | Billing plan reference (external billing system is source of truth; this is just a pointer). |
| `user_limit`, `monthly_task_limit` | integer/bigint, CHECK > 0 | Plan-enforced quotas, checked at the DB to guarantee they're never stored as nonsensical zero/negative values. |
| `created_at`, `updated_at` | timestamptz | Bookkeeping. |
| Index `tenants_status_ix` | (status) | Fast "list all active/suspended tenants" for ops dashboards. |

### 5.4 `tenant_settings`
1:1 config blob per tenant.

| Column | Why |
|---|---|
| `tenant_id` PK/FK, `ON DELETE CASCADE` | 1:1 extension of `tenants`; cascades naturally since settings are meaningless without the tenant. |
| `terminology` jsonb | Lets a tenant relabel domain terms in their UI (e.g. call "sites" "locations") without a schema change. |
| `task_policy` jsonb | Tenant-wide rules for task behavior (e.g. auto-assignment, SLA windows) — configurable, not code. |
| `evidence_policy` jsonb | Tenant default for required photo counts/signature rules, overridable per field. |
| `report_branding` jsonb | Logo/colors/footer text for generated PDF reports. |
| `feature_flags` jsonb | Per-tenant feature gating without a deploy. |
| `updated_at` | Config change tracking. |

### 5.5 `branches`
Physical/organizational sub-units of a tenant (offices, depots).

| Column | Why |
|---|---|
| `tenant_id, id` composite PK | Tenant-scoped identity pattern (see §2). |
| `code` citext, unique per tenant | Short human reference (e.g. "NYC-01"). |
| `name` | Display name. |
| `timezone` | Overrides tenant default for scheduling local to this branch. |
| `is_active` | Soft-disable a closed branch without deleting its history. |
| Index `branches_active_name_ix` | Supports the common "active branches sorted by name" picker query. |

### 5.6 `tenant_users`
Membership of a platform `user` inside a `tenant`, with role and reporting line — this is the row application code actually authorizes against day to day.

| Column | Why |
|---|---|
| `tenant_id, id` PK | Tenant-scoped membership identity (distinct from `user_id`, so the same person can have different `id`s/roles across tenants). |
| `user_id` FK → users, `ON DELETE RESTRICT`, unique per tenant | Links to the login identity; `RESTRICT` + uniqueness stop a user having two memberships in one tenant or vanishing while still referenced by tasks/audit rows. |
| `branch_id` FK → branches | Where this person is based, for branch-scoped dashboards/permissions. |
| `supervisor_tenant_user_id` FK → tenant_users (self) | Models the reporting hierarchy directly in the row, used for approval routing and "my team" queries. |
| `role` | membership_role | Coarse-grained permission tier (admin/supervisor/field_worker). |
| `status` | membership_status | Invitation lifecycle gating login. |
| `employee_code` citext, unique per tenant when set | Optional external HR/payroll identifier for matching against other systems. |
| `permission_overrides` jsonb | Fine-grained exceptions to the role default (e.g. one supervisor also allowed to edit workflows) without inventing more roles. |
| CHECK `tenant_users_not_own_supervisor_ck` | id ≠ supervisor_tenant_user_id | Trivial self-reference loop prevention. |
| Index `tenant_users_role_status_ix` | (role, status) | "All active supervisors" type queries for assignment pickers. |
| Index `tenant_users_branch_status_ix` | (branch_id, status) | Branch roster queries. |
| Index `tenant_users_supervisor_status_ix` | (supervisor, status) | "My direct reports" queries. |

### 5.7 `teams`
Groups of `tenant_users` that can be assigned work collectively.

| Column | Why |
|---|---|
| `branch_id` | Scopes the team to a location. |
| `code`, `name` | Identity/display. |
| `supervisor_tenant_user_id` | Team lead of record, for escalation/review routing distinct from individual members' personal supervisor. |
| `skills` jsonb | Tag-based matching for dispatch (e.g. "HVAC", "electrical") without a rigid skills table. |
| `is_active` | Soft-disable. |
| Indexes on `(branch_id, is_active)` and `(supervisor, is_active)` | Support team-picker and "teams I lead" queries. |

### 5.8 `team_members`
Join table: which `tenant_users` are/were in which `team`, over time.

| Column | Why |
|---|---|
| `is_lead` | Marks the on-team point of contact; enforced unique-per-team-while-active via `team_members_one_active_lead_uq`. |
| `joined_at`, `left_at` | Membership is time-ranged, not just boolean, so historical team rosters can be reconstructed for past tasks. |
| CHECK `team_members_dates_ck` | left_at ≥ joined_at | Basic temporal sanity. |
| Index `team_members_user_active_ix` (partial, `left_at IS NULL`) | Fast "what team(s) is this person currently on" lookup, ignoring historical rows. |

### 5.9 `customers`
The tenant's own clients (who they perform field service *for*).

| Column | Why |
|---|---|
| `customer_code` citext, unique per tenant | Human/ERP-friendly reference number. |
| `name`, `customer_type` | Identity and segmentation (e.g. "residential" vs "commercial"). |
| `contact_name`, `phone_e164`, `email` | Primary contact channel for scheduling/confirmations. |
| `billing_address` | Invoicing. |
| `notes` | Free-form account notes. |
| `is_active`, `deleted_at` | Soft lifecycle — customers are never hard-deleted because tasks/reports reference them permanently. |
| Index `customers_name_trgm_ix` (GIN, pg_trgm) | Fast fuzzy/typo-tolerant name search in the dispatcher UI. |

### 5.10 `sites`
A physical location belonging to a customer, where work happens.

| Column | Why |
|---|---|
| `customer_id` FK | Ownership. |
| `site_code` citext, unique per tenant | Human reference. |
| `address_line, city, region, postal_code` | Physical address for routing/dispatch. |
| `latitude, longitude` numeric(9,6) | Geocoded location for map views and GPS-proximity rule evaluation. |
| `geofence_radius_m` int, 10–50000 | Defines "on site" for GPS check-in/geofence rules; bounded to sane real-world values. |
| `contact_name`, `contact_phone_e164` | On-site point of contact. |
| `access_instructions`, `safety_instructions` | Operational text shown to the field worker before/at arrival (gate codes, hazards). |
| `working_hours` jsonb | Site-specific access windows, structured but variable (per-day hours), so JSON avoids a rigid weekly-hours table. |
| `is_active`, `deleted_at` | Same soft-lifecycle reasoning as customers. |
| `UNIQUE (tenant_id, id, customer_id)` | Composite uniqueness that lets *other* tables (e.g. `service_targets`, `tasks`) FK on `(tenant_id, site_id, customer_id)` simultaneously, so the DB enforces that a site's customer_id can't silently drift from what a child row expects. |
| CHECK lat/long ranges + pair-nullness | Prevents storing invalid coordinates or a lat without a long. |
| Index `sites_name_trgm`-style via `sites_active_name_ix` | Site picker performance. |

### 5.11 `service_targets`
The specific equipment/asset at a site that work is performed on (an AC unit, an elevator, a fire extinguisher).

| Column | Why |
|---|---|
| `site_id` FK | Physical location of the asset. |
| `target_code` citext, `qr_barcode` text, both unique-when-set | Two independent identification paths: an internal reference code and a scannable barcode/QR for the mobile app's "scan asset" flow. |
| `category`, `name`, `brand`, `model`, `serial_number` | Standard asset identity fields for reporting/warranty. |
| `capacity_value`, `capacity_unit` | Equipment sizing (e.g. "5 tons" for HVAC), kept as a value+unit pair rather than a fixed unit column since capacity units vary by category. |
| `installed_at`, `warranty_expires_at` | Lifecycle dates driving maintenance scheduling and warranty-aware repair decisions. |
| `floor_room_zone` | Fine-grained in-building location beyond the site address. |
| `condition_status` | Free-text current condition summary. |
| `metadata` jsonb | Category-specific attributes that vary too much (per equipment type) to model as fixed columns. |
| `is_active`, `deleted_at` | Assets get decommissioned, not deleted — task history must remain valid. |
| Indexes on `(site_id, is_active)`, `(category, is_active)`, `serial_number` | Support the asset-list, category-filtered, and serial-lookup query patterns. |

### 5.12 `parts`
Tenant's parts/materials catalog.

| Column | Why |
|---|---|
| `part_code` citext, unique per tenant | SKU-style reference. |
| `name`, `category`, `unit` | Catalog display and unit-of-measure for quantity tracking. |
| `compatibility` jsonb | Which equipment models/categories a part fits — variable-shape data, not worth a join table for a catalog attribute. |
| `is_active` | Discontinue without deleting (parts history must survive). |
| Index `parts_name_trgm_ix` | Fuzzy search when a technician is picking a part in the field. |

### 5.13 `workflows`
The named "template family" for a type of job (e.g. "HVAC Preventive Maintenance"). The actual form structure lives in versions.

| Column | Why |
|---|---|
| `code` citext, unique per tenant | Stable reference usable in integrations/imports. |
| `name`, `description` | Display. |
| `industry_category`, `work_type` | Classification for filtering/analytics and for matching against recurrence plans/tasks. |
| `target_required` boolean | Whether tasks using this workflow must be tied to a `service_target` (e.g. "site inspection" workflows might not need one; "repair this unit" workflows do). |
| `status` workflow_status | Whether new tasks can still pick this workflow family. |
| `current_published_version_id` | Fast pointer to the live version, avoiding a subquery on `workflow_versions` for the common "get the active form" read path. |
| `created_by_tenant_user_id` | Authorship/audit. |
| FK `workflows_published_version_fk` (added after `workflow_versions` exists) | Ensures the pointer always references a version that actually belongs to *this* workflow — a 3-column FK `(tenant_id, current_published_version_id, id)` against `workflow_versions(tenant_id, id, workflow_id)`. |

### 5.14 `workflow_versions`
Immutable, versioned snapshots of a workflow's structure — this is what tasks actually bind to, so live tasks are never affected by in-progress edits.

| Column | Why |
|---|---|
| `workflow_id` FK | Parent template family. |
| `version_no` int, CHECK > 0, unique per workflow | Simple incrementing version identity, human-meaningful ("v3"). |
| `status` workflow_version_status | draft (editable) → published (immutable, usable by tasks) → archived. |
| `configuration` jsonb | Denormalized full-form snapshot (fast to load as a single blob for the mobile client) *in addition to* the normalized `workflow_sections`/`workflow_fields`/`workflow_rules` tables below — the normalized tables are the editable source of truth and support relational queries (e.g. "which fields reference this lookup"); the JSON is a compiled artifact for runtime consumption. |
| `change_summary` | Human changelog entry between versions. |
| `created_by_tenant_user_id`, `published_by_tenant_user_id` | Separate authorship of the draft vs. who approved publishing it — supports a maker/checker workflow-builder process. |
| `published_at`, `archived_at` | Lifecycle timestamps. |
| CHECK `workflow_versions_publish_ck` | published ⇒ published_at & published_by set | Data integrity: can't be "published" without recording who/when. |
| Unique index `workflow_versions_one_published_uq` (partial, status='published') | At most one live version per workflow at a time — the single most important invariant for this table. |

### 5.15 `workflow_sections`
Ordered groupings of fields within a version (e.g. "Safety Check", "Readings").

| Column | Why |
|---|---|
| `section_key` | Stable machine key (used in rule targets, calculated-field references, report templates) independent of the display `title`, so renaming a section's label doesn't break rules. |
| `title`, `description` | Display. |
| `position` int, unique per version | Explicit ordering (rather than relying on insertion order) since sections can be reordered in the builder. |
| `is_repeatable` | Marks a section that itself can repeat (distinct from `repeatable_group` fields) — supports "repeat this whole block N times" form patterns. |
| `settings` jsonb | Section-level display/behavior config not worth dedicated columns. |
| `UNIQUE (tenant_id, id, workflow_version_id)` | Lets `workflow_fields` FK on `(tenant_id, section_id, workflow_version_id)`, guaranteeing a field's section always belongs to the same version as the field. |

### 5.16 `workflow_fields`
The individual form controls. Supports nesting via `parent_group_field_id` for repeatable groups.

| Column | Why |
|---|---|
| `section_id` FK | Placement. |
| `parent_group_field_id` FK → workflow_fields (self) | Enables `repeatable_group` fields to contain child fields (e.g. a "parts replaced" repeating row with its own sub-fields), modeled as a self-referencing tree rather than a separate nested schema. |
| `field_key` unique per version | Stable machine reference for rules, calculated-field formulas, and answer storage — decoupled from the editable `label`. |
| `field_type` | Which of the ~19 widget types this is (see `field_type` enum). |
| `label`, `description`, `placeholder` | Display/UX text. |
| `position` unique per section | Explicit ordering within the section. |
| `required_by_default` | Baseline requiredness before any conditional rule overrides it. |
| `read_only` | Field is display-only (e.g. shows a lookup's snapshot value), not directly editable by the worker. |
| `default_value` jsonb | Pre-filled value; JSON because the shape depends on `field_type` (string, number, array of option keys, etc.). |
| `validation` jsonb | Type-specific validation rules (min/max, regex, required option count) — kept flexible because validation shape differs wildly per field type. |
| `evidence_policy` jsonb | Per-field override of tenant evidence defaults (e.g. "this photo field requires GPS-tagged capture only, no gallery uploads"). |
| `report_policy` jsonb | Controls how this field's answer appears in the generated report (visibility, formatting). |
| `privacy_policy` jsonb | Marks sensitive fields for redaction/access control in reports and exports. |
| `UNIQUE (tenant_id, id, workflow_version_id)` | Enables downstream tables (options, rule conditions/actions, answers) to FK on `(tenant_id, field_id, workflow_version_id)` and guarantee cross-version references are impossible. |
| Index `workflow_fields_parent_ix` | Fast retrieval of a group's children in position order. |

### 5.17 `workflow_field_options`
Choices for `single_choice`/`multiple_choice` fields.

| Column | Why |
|---|---|
| `field_id` FK | Owning field. |
| `option_key` unique per field | Stable machine value stored in answers/rules, independent of the editable `label`. |
| `label` | Display text. |
| `position` unique per field | Explicit choice ordering. |
| `is_active` | Retire an option (e.g. deprecated equipment type) without breaking historical answers that reference it. |
| `metadata` jsonb | Extra per-option data (e.g. a score value, a color code) without new columns. |

### 5.18 `workflow_rules`
Named conditional-logic rules ("if X then Y") scoped to a version.

| Column | Why |
|---|---|
| `name` unique per version | Human identity for the builder UI/debugging. |
| `priority` int | Execution order when multiple rules could fire, so results are deterministic. |
| `is_active` | Disable a rule without deleting it (keeps history/authoring intact). |
| `stop_processing` | Short-circuits lower-priority rules once this one matches — needed to express "if safety_stop, ignore everything else." |
| Index `workflow_rules_priority_ix` | Engine loads a version's rules in priority order efficiently. |

### 5.19 `workflow_rule_conditions`
The "if" side of a rule — one row per condition, grouped/joined by conjunction.

| Column | Why |
|---|---|
| `rule_id` FK | Owning rule. |
| `source_field_id` FK, nullable | Field whose answer is being tested; nullable to allow non-field-based conditions (e.g. system context) in future without schema change. |
| `group_no` int | Groups conditions for `(A and B) or (C and D)`-style nested boolean logic — flat rows plus a group number is a simpler storage model than a recursive expression tree while still expressing 2-level boolean logic. |
| `position` unique per (rule, group) | Ordering within a group. |
| `conjunction` | and/or joiner to the next condition. |
| `operator` | Which of the 29 `rule_operator` comparisons to apply. |
| `comparison_value` jsonb | The right-hand side of the comparison; JSON because the operand shape varies by operator (scalar, range, list of option keys). |
| Index `workflow_rule_conditions_field_ix` | Given a field, find every rule that reacts to it — used both by the runtime engine and by "what depends on this field" impact analysis in the builder UI. |

### 5.20 `workflow_rule_actions`
The "then" side of a rule.

| Column | Why |
|---|---|
| `rule_id` FK | Owning rule. |
| `target_field_id` / `target_section_id` | What the action applies to; mutually exclusive by design. |
| `position` unique per rule | Ordering when a rule has multiple actions. |
| `action_type` | Which of the 17 `rule_action_type` effects to apply. |
| `action_value` jsonb | Action-specific payload (e.g. the value to set, the message text to show) — shape depends on `action_type`. |
| CHECK `workflow_rule_actions_target_ck` | `num_nonnulls(target_field_id, target_section_id) <= 1` | An action targets at most one of field-or-section (some actions like `block_submission` target neither). |
| Indexes on both target columns | Reverse lookup: "what rules affect this field/section" for builder UI and engine evaluation. |

### 5.21 `recurrence_plans`
A standing schedule that auto-generates `tasks` (e.g. quarterly maintenance).

| Column | Why |
|---|---|
| `plan_code` unique per tenant | Human reference. |
| `customer_id`, `site_id`, `service_target_id` | What the recurring work is for; `service_target_id` optional since not all recurring work targets a specific asset. Composite FKs (`tenant_id, site_id, customer_id` etc.) enforce the referenced site actually belongs to the referenced customer, and the target to the site. |
| `workflow_id` | Which checklist template family to use each time (not a specific version — each generated task binds to whatever is published at generation time). |

| `responsible_lead_id` | Accountable supervisor for the plan, independent of who's actually assigned to do the work. |
| `schedule_rule` jsonb, NOT NULL | The recurrence pattern (e.g. RRULE-like frequency/interval) — inherently structured-but-variable, so JSON over a rigid cron-columns model. |
| `timezone` | Recurrence must be evaluated in a specific timezone (not UTC) so "every Monday at 9am" means the same local time regardless of DST. |
| `starts_on`, `ends_on` | Validity window; `ends_on` nullable for open-ended plans. |

| `next_generation_at` | Drives the background job that materializes upcoming tasks — indexed for efficient "what's due to generate" scans. |
| `status` recurrence_status | draft/active/paused/ended lifecycle, independent from any individual generated task's status. |
| CHECK `recurrence_plans_dates_ck` | ends_on ≥ starts_on | Basic sanity. |
| Index `recurrence_plans_generation_ix` | (status, next_generation_at) — the exact predicate the generation job scans on. |

| Column | Why |

| Partial index `tasks_active_due_px` | Only rows in open statuses — keeps the hot "what's outstanding" index small and fast as closed history accumulates. |

### 5.25 `device_installations`

| Column | Why |

### 5.26 `task_runs`
One *submission attempt* of a task's workflow. A rejected submission creates a new run rather than mutating the old one — this is the immutability backbone for audit/compliance.

| Column | Why |
|---|---|
| `task_id` FK | Owning task. |
| `workflow_version_id` FK, matched against the task's own version via composite FK | Guarantees a run always uses the exact version the task was created against. |
| `run_no` int, unique per task | Increments each attempt (1st submission, resubmission after rejection, etc.) — human-traceable attempt number. |
| `state` task_run_state | draft (in progress) → submitted → rejected/approved. |
| `result` task_result | This attempt's outcome. |
| `performed_by_tenant_user_id` | Who actually did the work (may differ from the task's assignee in helper scenarios). |
| `device_id` | Which device the run was performed/submitted from — supports debugging sync issues and proving field conditions. |
| `started_at`, `submitted_at` | Duration tracking; CHECK `task_runs_submission_ck` requires `submitted_at` once the state leaves `draft`. |
| `offline_started` | Marks a run that began without connectivity — relevant for reviewing GPS/timestamp trust. |
| `app_version` | Reproduce client-specific bugs affecting a submission. |
| `declaration_accepted_at` | Timestamp of the worker accepting a completion declaration/attestation (e.g. "I confirm this work was performed safely"), a common compliance requirement. |
| `UNIQUE (tenant_id, id, task_id)` | Lets every child table (answers, evidence, exceptions, reviews...) FK on `(tenant_id, task_run_id, task_id)` to guarantee a run's children always trace back to the correct parent task. |

### 5.27 `task_status_history`
Append-only log of every status transition on a task.

| Column | Why |
|---|---|
| `id` bigint identity | High-volume append-only log; a simple sequence is cheaper than a UUID here and ordering by insertion is meaningful. |
| `task_id`, `task_run_id` | What changed and in the context of which submission attempt (nullable — some transitions aren't run-specific). |
| `from_status`, `to_status` | The transition itself, for building a full timeline. |
| `reason_code`, `reason_text` | Structured + free-text explanation (e.g. cancellation or rejection reason). |
| `changed_by_tenant_user_id` | Nullable to allow system-driven transitions (e.g. an auto-expiry job) with no human actor. |
| `occurred_at` | When it happened. |
| CHECK `task_status_history_transition_ck` | from ≠ to | A "transition" that doesn't change anything isn't a transition. |
| Index `task_status_history_task_time_ix` | Reconstruct a task's timeline in order. |
| BRIN index `task_status_history_time_brin` | This table is append-only and time-correlated with insertion order — BRIN gives near-btree range-query performance at a fraction of the storage/maintenance cost, ideal for a fast-growing log table. |

### 5.29 `task_answers`
The actual captured value for one field (optionally within one repeat-group instance) in one run.

| Column | Why |
|---|---|
| `task_run_id`, `field_id` | What's being answered and in which submission. |
| `repeat_group_instance_id` | Nullable — set only when the field lives inside a repeating group instance. |
| `text_value, numeric_value, boolean_value, date_value, time_value, timestamp_value, json_value` | One typed column per possible answer shape rather than a single "value" jsonb column — this keeps native type constraints, indexing, and numeric/date comparisons possible directly in SQL (important for rule evaluation and reporting aggregation) while `json_value` remains as the escape hatch for complex/structured answers (e.g. GPS coordinates as a compound value). |

| `validation_status`, `validation_messages` | Result of the field's `validation` rules applied to this specific value, cached rather than recomputed on every read. |

| CHECK lat/long range + pairing | Same coordinate-sanity pattern as `sites`/`evidence_files`. |
| Unique index `task_answers_scalar_uq` | One answer per (run, field) for non-repeating fields. |
| Unique index `task_answers_repeat_uq` | One answer per (run, group instance, field) for repeating fields — the two partial unique indexes together enforce "exactly one answer per field occurrence" regardless of whether it's inside a repeat group. |
| Index `task_answers_field_validation_ix` | "All invalid/warning answers for this field across runs" for QA/reporting. |

### 5.33 `evidence_files`
Metadata for photos/files/signatures. Actual bytes live in object storage (see design notes, §7) — this table is the durable, queryable pointer + audit record.

| Column | Why |

| `answer_id` | Nullable — links evidence to a specific field's answer when applicable (vs. general task-level attachments). |

| `evidence_type` | image/file/signature. |

### 5.34 `gps_events`
Raw location breadcrumbs — proof of presence.

| Column | Why |
|---|---|
| `id` bigint identity | High-volume append-only telemetry; sequence over UUID for the same reason as `task_status_history`. |
| `task_id`, `task_run_id` | Context (run nullable — e.g. `duty_start`/`duty_end` aren't tied to a specific run). |

### 5.41 `sync_mutations`
Log of every offline mutation a device has replayed to the server — the idempotency ledger for offline-first sync.

| Column | Why |
|---|---|
| `mutation_id` uuid, client-generated, PK (with tenant_id) | The client assigns this before ever reaching the server; replaying the same mutation twice (common on flaky connections) is naturally deduped by the PK, giving exactly-once semantics without server-side coordination. |
| `device_id` | Which device originated it. |
| `task_id` nullable | Most mutations relate to a task, but not necessarily all. |
| `entity_type`, `entity_id`, `operation` | What was mutated and how (generic enough to log mutations against any offline-editable entity, not just tasks). |
| `payload_hash` char(64) | Detects a client resending materially different data under an id that was already processed (contents changed vs. pure retry) without storing the full payload here. |

|---|---|

## 6. Security model

### 6.1 Row-Level Security
Every tenant-scoped table gets:
```sql
ALTER TABLE field_ops.<table> ENABLE ROW LEVEL SECURITY;
ALTER TABLE field_ops.<table> FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON field_ops.<table>
  USING (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);
```
- `ENABLE` turns RLS on for normal users; `FORCE` additionally applies it to
  the table owner, so even the application's own DB role can't accidentally
  bypass it.
- The policy reads `app.tenant_id`, which the application **must** set with
  `SET LOCAL app.tenant_id = '<uuid>'` at the start of every transaction.
  `nullif(..., '')` means an unset/empty setting resolves to `NULL`, which
  matches nothing — a transaction that forgets to set tenant context sees
  zero rows rather than all tenants' rows, which fails safely (visibly
  broken) instead of leaking data silently.
- `USING` gates reads/updates/deletes; `WITH CHECK` gates inserts/updates —
  both are needed so a session can't read tenant A's context but write into
  tenant B.

Tables *not* under RLS: `users`, `platform_admins`, `tenants` — these are
platform-level, not owned by a single tenant, so tenant isolation doesn't
apply to them by definition.

### 6.2 Why composite `(tenant_id, ...)` foreign keys everywhere
Standard single-column foreign keys only guarantee the referenced row
exists — they say nothing about which tenant it belongs to. By carrying
`tenant_id` through every FK (e.g. `sites` FKs to
`customers(tenant_id, id)`, not just `customers(id)`), the database itself
refuses to let a row reference another tenant's data, independent of RLS.
This is why almost every table's primary key is `(tenant_id, id)` rather
than a bare `id`.

## 7. Operational notes (from the schema's own trailing comment block)

These are called out in the SQL file as **deployment guidance to apply
after workload testing**, not defaults baked into the DDL:

1. **Partition high-volume append-only tables** (`task_status_history`,
   `gps_events`, `sync_mutations`, `audit_logs`) by month once they grow
   large — they're insert-heavy, time-ordered, and rarely updated, which is
   the ideal partitioning shape.
2. **Consider partitioning `tasks`** by time/tenant only if scale actually
   demands it — don't do it preemptively.
3. **Add PostGIS** (`geography(Point,4326)` + GiST) if radius/nearest-site
   queries become frequent — the current lat/long `numeric` columns are
   sufficient for storage and simple bounding checks but not for efficient
   proximity search at scale.
4. **Keep evidence bytes out of Postgres.** `evidence_files` is metadata
   only; actual image/file bytes belong in object storage (S3-compatible),
   referenced by `object_key`.
5. **Use read replicas/materialized views for dashboards** rather than
   pointing analytics queries at the OLTP indexes designed for
   transactional workloads.
6. **Deny UPDATE/DELETE at the privilege level** on published
   `workflow_versions`, submitted `task_runs`, `evidence_files` metadata,
   and `audit_logs` — the schema models these as *logically* immutable
   (via CHECK constraints and application discipline), but true
   immutability requires revoking the privilege from the application's DB
   role, which is a deployment-time step, not DDL.

## 8. Reading the schema top to bottom

The table creation order in the `.sql` file follows the dependency graph
and roughly the conceptual layers of the system:

1. **Identity & tenancy** — `users` → `tenants` → `tenant_settings` →
   `branches` → `tenant_users` → `teams`/`team_members`
2. **Reference data** — `customers` → `sites` → `service_targets` → `parts`
3. **Workflow builder (the form designer)** — `workflows` →
   `workflow_versions` → `workflow_sections` → `workflow_fields` →
   `workflow_field_options` → `workflow_rules` →
   `workflow_rule_conditions`/`workflow_rule_actions`
4. **Scheduling** — `recurrence_plans` → `tasks` → `task_assignments` →
   `task_links` → `device_installations`
5. **Execution (mobile submission)** — `task_runs` →
   `task_status_history` → `repeat_group_instances` → `task_answers` →
   `answer_option_selections`/`answer_lookup_selections` →
   `task_section_results` → `evidence_files` → `gps_events` →
   `parts_used` → `otp_challenges` → `customer_confirmations`
6. **Review & exceptions** — `task_exceptions` → `task_reviews` →
   `target_registration_requests`
7. **Platform plumbing** — `sync_mutations` → `import_jobs`/`import_rows`
   → `notifications` → `generated_reports` → `audit_logs`

This is also the recommended reading order for anyone new to the schema:
understand tenancy first, then reference data, then how a workflow is
*designed*, then how a task is *scheduled*, then how it's *executed* in
the field, then how it's *reviewed*, then the cross-cutting plumbing.
